## 1. 독립 검토 결론 — 왜 골격은 유지했나

기존 코드를 백지에서 다시 읽고, 같은 문제를 처음부터 설계한다면 어떻게 할지 문헌과 대조했다.

**기존 연구(TCLP, tower crane location problem) 경향:**
- 대다수가 **운반시간·비용 최소화 단일목적**이다. GA로 총 운반시간을 최소화(Tam & Tong 계열), MILP로 hook travel time을 최소화(Huang et al.), CBO/VPS 등 메타휴리스틱으로 운반비용 최소화 — 전부 Zhang의 후크 이동시간(선회·횡행·권상 3자유도) 모델 위에 서 있다.
- 안전을 다루는 연구도 **크레인 간 교차면적 최소화**(다중 크레인 충돌)나 **양중모멘트**(장비 자체 안전) 관점이다. 홍콩 MiC 사례의 NSGA-III 연구가 대표적인데, 안전 목적함수가 lifting moment다.
- 즉 **"부지 밖 제3자(도로 보행자·인접 주민)가 얼마나 노출되는가"를 목적함수로 정량화해 Pareto 축에 올린 사례는 드물다.** 협소대지에서는 선회반경이 필연적으로 대지 밖으로 나가므로, 이게 v1의 진짜 차별점이고 — 유지가 맞다.

**알고리즘·플랫폼:** 2목적 연속변수 + 비선형 제약 9개 구조에서 NSGA-II는 표준 선택이고, pymoo는 검증된 구현이다. Streamlit + GitHub 자동배포 파이프라인은 이미 동작 중이고 사용자(작성자)의 유지보수 능력 범위 안에 있다. 갈아엎으면 검증 자산(신사동·방배동)만 잃는다.

**그래서 v2 전략 = 골격 유지 + 약점 3개 수술.** 차별점은 구조가 아니라 ① 위험모델의 규정 정합성, ② 추천의 재현 안정성, ③ 설명력에서 만든다.

## 2. 발견한 문제 ①: 단일 seed 추천의 불안정 (가장 중요)

### 2-1. 실험

신사동 19-147, v1 그대로 (pop=80, gen=40, per_model, robust knee), 실제 크레인 위치 (-0.3, 6.5) 기준:

| seed | knee 위치 | 기종 | 실제와 거리 | Pareto 수 |
|---|---|---|---|---|
| 0 | (-2.82, **-6.79**) | MR 160C | **13.53 m** | 43 |
| 1 | (-1.41, 8.00) | MR 160C | 1.86 m | 70 |
| 2 | (-0.76, 7.86) | 280 HC-L | 1.43 m | 81 |
| 3 | (-2.03, 7.83) | MR 160C | 2.19 m | 41 |
| 4 | (-1.41, 7.97) | MR 160C | 1.85 m | 53 |
| 5 | (-1.69, 7.99) | MR 160C | 2.04 m | 63 |
| **42** | (**13.22, -14.89**) | MR 160C | **25.30 m** | 21 |

- 평균 6.88 m, 중앙값 2.04 m, 범위 [1.43, 25.30].
- 5/7 seed는 논문 주장(~1.6 m)을 재현. **그러나 seed 0과 42는 front 전체가 다른 국소영역(basin)에 정착** — Pareto 수가 21개로 작고 위치가 통째로 다르다. front 안에서 이상치를 제거하는 robust knee로는 교정 불가(front 자체가 이상치라서).
- **치명적인 점: 앱의 하드코딩 기본 seed가 42다.** 누군가(예: 심사자) 배포 앱을 기본 설정으로 열어 신사동을 돌리면 논문과 25 m 다른 답을 본다.

### 2-2. 정직한 해석

이건 v1 구현 버그가 아니라 **메타휴리스틱의 본질적 확률성**이다. NSGA-II는 확률적 탐색이라 seed에 따라 다른 basin에 수렴할 수 있다. 문제는 "단일 seed 1회 실행 = 추천"이라는 v1의 운영 방식이었고, 논문의 1.6 m 주장은 "좋은 seed들의 결과"였던 셈이다. 이걸 숨기지 않고 정면으로 다루면 오히려 논문이 강해진다(아래 §7).

## 3. 해법 ①: 다중 seed 합의(consensus) 추천

### 3-1. 메커니즘

```
K개 seed로 NSGA-II 독립 실행
  → K개 Pareto front를 합집합(union)
  → 합집합에 비지배 정렬(non-dominated sorting) 재적용
  → 살아남은 통합 front에서 robust knee 선정
  → 부가 출력: seed별 knee 간 최대 편차(합의도, m)
```

핵심 원리: **나쁜 basin의 해는 좋은 basin의 해에 지배(dominated)되어 합집합 정렬에서 자동 탈락**한다. 다수결이 아니라 Pareto 지배 관계가 필터다.

### 3-2. 검증 — 나쁜 seed를 일부러 포함

| seed 조합 | 통합 front | 합의 knee | 실제와 거리 | seed별 knee 최대편차 |
|---|---|---|---|---|
| {42, 0, 1} (나쁜 2 + 좋은 1) | 62 | (-1.77, 7.94) | **2.06 m** | 27.2 m |
| {42, 0, 1, 2, 3} | 123 | (-0.76, 7.86) | **1.43 m** | 27.4 m |

개별 seed는 최대 27 m씩 흩어졌지만 합의 knee는 1.4~2.1 m. **불안정성이 구조적으로 제거**됐다.

### 3-3. 앱 반영

- 탭③에 "다중 seed 합의" 토글 **기본 ON**, seed 수 슬라이더(기본 3 = seeds 0,1,2, 약 70~90초).
- 실행 후 "합의도: seed 간 추천 편차 최대 X.X m" 표시 — 작으면 그 자체가 신뢰 근거, 크면 합의가 일을 했다는 뜻.
- 단일 seed 모드도 남겨둠(빠른 데모용). API: `optimizer.run_consensus_optimization(pop_size, n_gen, seeds, per_model, progress_cb)` → `(F, X, info)`.

## 4. 해법 ②: 운영가중 노출 F1 모드 (방법론 차별점)

### 4-1. 규정 근거

낙하물 위험은 선회원판 전체에 균일하지 않고 **"하중이 매달려 지나가는 경로" 아래에 집중**된다는 게 안전규정의 공통 원칙이다:

- **OSHA 29 CFR 1910.179(n)(3)(vi)**: "The employer shall require that the operator avoid carrying loads over people" — 적재 하중을 사람 위로 통과시키지 말 것.
- **영국 HSE** (Health and Safety in Construction / LOLER 지침): 점유 구역 위로 하중을 매달아 통과시키지 않도록 양중계획을 수립할 것.

v1의 정적 F1(선회원판 전체 균일 노출)은 보수적이지만, "어느 방향으로 적재 하중이 실제로 다니는가"를 구분하지 못한다. 야적장이 도로 쪽에 있으면 도로 위 통과가 잦아 실제 위험이 더 크고, 반대면 더 작다 — 정적 모드는 둘을 같은 점수로 본다.

### 4-2. 모델

야적장→각 양중점 사이클의 **적재(loaded) 구간**이 각 방위각 빈 θ에 머무는 시간 비중 w(θ)를, v1과 동일한 크레인 속도 사양(권상·선회·횡행/기복)으로 계산:

```
F1_op = (위험가중 사이클수 × P_base) × Σ_θ w(θ)·V(θ)·B

  w(θ): 적재 후크의 방위각 체류분포 (끝점 권상·하강 체류 + 호(arc) 선회 분배)
  V(θ): 빈 θ의 부채꼴 취약가중 면적 (도로 5.0 / 인접건물 3.0 / 자기부지 0.5 / 공지 1.0 — v1과 동일 가중)
  B = 72빈(5° 간격), 반경 10등면적 샘플
```

구현: 부지 전환 시 1 m 해상도 취약성 raster를 1회 생성(`shapely.contains_xy` 벡터화), 평가 시 격자 조회만 — **1.59 ms/eval**로 NSGA-II 안에서 무리 없음.

### 4-3. 검증 3종 (모두 통과)

1. **특수해 일치**: w(θ)를 균일분포로 강제하면 정적 F1의 가중면적과 **0.2% 이내 일치** (508.1 vs 508.9, raster 이산화 오차). → 정적 모드 = 운영 모드의 특수해. 논문 수치는 깨지지 않는다.
2. **판별력**: 같은 부지에서 위치 (-8, 2)는 적재 경로가 취약구역 쪽에 몰려 정적 대비 **×1.70** (225.3→397.9), 위치 (8, 8)은 경로가 취약구역을 피해 **×0.72** (262.4→188.1). 정적 모드가 동일하게 보던 위치들을 실제 운영 기준으로 구분한다.
3. **신사동 합의 최적화 비교** (seeds 0,1,2 / pop 80 / gen 40):

| F1 모드 | 합의 knee | 실제와 거리 | seed 간 합의도 |
|---|---|---|---|
| 정적 (논문 기준) | (-0.76, 7.86) | 1.43 m | 14.9 m |
| 운영가중 | (-0.74, 7.88) | **1.45 m** | **1.2 m** |

실제 시공 위치가 **두 모델 모두에서 근사 최적** — 검증이 한 겹 더 두꺼워졌고, 운영 모드에서는 seed 간 합의도까지 1.2 m로 조여져 탐색 지형이 더 또렷해졌다.

### 4-4. 명시적 단순화 (논문에 그대로 쓸 것)

- 방위각만 해상(resolved)하고 반경 방향은 부채꼴 전체 적분 — 낙하물 산란·지브 자체의 상공 점유를 고려한 보수적 선택이며, 반경해상 모델은 후속 과제.
- 야적장 위치는 부지 JSON의 `material_yard`를 사용(UI 직접 입력은 아직 없음).
- **기본 모드는 정적(논문 재현용)**, 운영 모드는 탭③ 라디오로 선택.

## 5. 해법 ③: ➕ 내 현장 만들기 버그 — 근본원인이 달랐다

인계문서의 추정은 "`use_site` 전역변수와 `st.rerun()` 타이밍 문제"였는데, 코드를 따라가 보니 **진짜 원인은 사이드바의 현장 목록 함수에 붙은 `@st.cache_data`**였다. 저장 직후 `st.rerun()`이 돌아도 캐시가 살아 있어 새 JSON 파일이 목록에 반영되지 않았던 것.

수정:
- `_list_available_sites`의 `@st.cache_data` 제거 (파일 glob은 충분히 싸다) + 사용자 현장을 mtime 최신순 정렬.
- 저장 시 `st.session_state["pending_site_sel"]`에 새 현장 이름을 적고 rerun → 다음 런에서 **사이드바 selectbox 위젯이 생성되기 전에** 이 값을 위젯 키(`site_sel_name`)로 옮겨 자동 선택. (Streamlit은 위젯 생성 후 해당 키 수정을 금지하므로 pending 키 우회가 정석.)
- 성공 안내는 `flash_msg` 세션 키로 rerun 이후 사이드바에 1회 표시.
- 부수: 다중 사용자가 동시에 실행하면 `use_site` 전역이 충돌할 수 있어 `optimizer.RUN_LOCK`(threading.Lock, 모듈 전역이라 rerun에도 유지)으로 최적화 실행을 직렬화하고, 잠금 안에서 활성 부지를 재동기화.

**검증**: Streamlit 공식 AppTest로 헤드리스 UI 테스트 — 1차 런 8개 현장 → ➕ 탭 폼 입력·저장 → 2차 런 9개 현장 + "⭐ 테스트현장" 자동 선택 확인. (`dev/v2_apptest_sidebar.py`)

## 7. GitHub 웹에디터 반영 절차 (네 워크플로 그대로)

> 익숙한 방식 그대로: github.com/mingyuuuu20/crane-optimizer 에서 파일 열기 → ✏️ → 전체 선택·삭제 → 새 내용 붙여넣기 → Commit changes. 클라우드는 1~2분 내 자동 재배포.

1. **explain.py (신규)**: 저장소 메인 화면 → `Add file` → `Create new file` → 파일명 `explain.py` → tar의 `explain.py` 내용 전체 붙여넣기 → Commit.
2. **objectives.py**: 파일 열기 → ✏️ → 전체 교체 → Commit.
3. **optimizer.py**: 동일.
4. **app.py**: 동일. (이 커밋이 들어가는 순간 새 UI가 뜬다)
5. 배포 확인: crane-optimizer.streamlit.app 새로고침 → 탭③에 "다중 seed 합의" 토글과 F1 모드 라디오가 보이면 성공. ➕ 탭에서 아무 현장이나 저장해 사이드바에 ⭐로 즉시 뜨는지 확인.
6. (선택) `dev/v2_*.py` 4개는 재현 실험용 — 올리고 싶으면 `dev/` 폴더에 같은 방식으로 Create new file.

문제 생기면: Streamlit Cloud 앱 우하단 `Manage app` → 로그에서 에러 줄 확인. import 에러면 1번(explain.py) 누락이 십중팔구.

## 8. 논문·발표 반영 제안

**재현성/한계 절에 추가할 내용 (그대로 다듬어 써도 됨):**

> NSGA-II는 확률적 탐색이므로 단일 난수 seed의 추천은 국소영역 의존성을 가질 수 있다. 신사동 사례 7-seed 실험에서 5개 seed는 실제 설치 위치 1.4~2.2 m 이내로 수렴했으나 2개 seed는 13~25 m 이격된 별도 영역에 정착하였다. 이에 본 시스템은 K개 seed의 Pareto front 합집합에 비지배 정렬을 재적용하는 합의(consensus) 추천을 기본으로 채택하였으며, 열등 영역의 해가 지배 관계에 의해 자동 배제됨을 확인하였다(나쁜 seed 포함 시에도 합의 knee 1.43~2.06 m 유지). 아울러 seed 간 추천 편차(합의도)를 신뢰 지표로 함께 제시한다.

**고찰(방법론 차별성) 절:**

> 기존 TCLP 연구는 후크 운반시간·비용 최소화를 주 목적으로 하며, 안전은 크레인 간 간섭이나 양중모멘트 등 장비 중심 지표로 다뤄 왔다. 본 연구는 부지 외부 제3자 노출을 목적함수 축으로 정량화하였고, 나아가 OSHA 1910.179(n)(3)(vi) 및 HSE 양중계획 지침의 "적재 하중 경로" 원칙에 따라 적재 후크의 방위각 체류분포로 노출을 가중하는 운영 모드를 제시하였다. 균일 체류분포 가정 시 본 모드는 정적 선회면적 평가로 환원되므로(0.2% 이내 일치), 정적 모형은 제안 모형의 특수해에 해당한다. 신사동 검증에서 실제 설치 위치는 두 모형 모두에서 근사 최적이었다(1.43 m / 1.45 m).

발표 Q&A 대비 — "seed 바꾸면 답 달라지지 않냐?"는 단골 질문인데, 이제 "맞다, 그래서 측정했고(7-seed 표), 합의 메커니즘으로 구조적으로 해결했다(검증 표)"로 정면 대응 가능. 약점이 방어 논리로 바뀐 것.
